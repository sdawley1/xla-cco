## Notes and caveats

- Mechanism: the per-(k,j) cost drops from one sin and one cos (twice: density and gradient) to d-1 complex multiplications per axis-gathered phase; the tables cost O(n_max N d) trig-free cumulative products. A direct-trig table is slower on XLA CPU (see rejected row).
- The fast path needs a static bound on |n_a|, so `StealthyEnergy` gained one defaulted static field `n_max` (appended after `chunk_size`; `make_stealthy_energy` sets it; `None`, the value for hand-built energies, keeps the trig path). An under-sized `n_max` gives NaN, never a silently wrong finite value. `__call__` and `collective_density` are unchanged (plain jnp, Hessian-safe).
- GPU relax with L-BFGS at chi 0.05 (M = 13 padded to 64) is slower with tables (0.46x, identical eval counts), as are chi 0.1 and 0.2 (grid below). This is why the factory only enables tables for M >= 75.
- GPU chi = 0.45 L-BFGS eval counts differed between the two paths (557049 trig vs 522457 tables), so the per-eval speedup is 1.27x against 1.36x in wall time.
- Case B on the A100 gains only 1.12x (below the 1.3x bar); on CPU 2.4x. A100 80 GB would hold case B even unchunked; the chunked path peaks at 0.17-0.24 GiB.
- chi 0.05 pads M = 13 to 64 (factory `pad_to=64`), so about 5x of the work is zero-weight rows on both paths.
- CPU numbers were taken on a shared login node pinned to 8 cores; CPU relax uses batch 64 (batch 256 was killed by the login node), GPU relax uses batch 1000.

## Fix round 1: tables-vs-trig rule (R26)

GPU grid (`benchmarks/bench_threshold.py`, job 16983169, A100-SXM4-80GB): L-BFGS `relax`, d=3, N=100, batch 1000, `max_evals_per_pass`=200, 3 warm repeats (spread under 1%), trig vs tables on identical configurations. Raw data: `benchmarks/results_threshold_gpu.json`.

| chi | M | max abs n | evals trig / tables | warm s trig | warm s tables | wall speedup | per-eval speedup |
|---|---|---|---|---|---|---|---|
| 0.05 | 13 | 1 | 455419 / 455458 | 1.56 | 3.46 | 0.45x | 0.45x |
| 0.1 | 28 | 2 | 461749 / 460707 | 2.03 | 4.39 | 0.46x | 0.46x |
| 0.2 | 61 | 3 | 458780 / 459995 | 2.70 | 6.16 | 0.44x | 0.44x |
| 0.3 | 89 | 3 | 457528 / 456727 | 5.40 | 4.08 | 1.32x | 1.32x |
| 0.45 | 128 | 4 | 557049 / 522457 | 15.53 | 11.45 | 1.36x | 1.27x |

Findings: tables lose (0.44-0.46x) at M = 13, 28, 61 and win (1.27-1.36x per eval) at M = 89, 128. A rule on max|n| cannot separate them (max|n| = 3 at both M = 61, a loss, and M = 89, a win), so the rule uses the number of k-vectors, which is a property of the k-set and independent of the backend.

**Chosen rule** (`make_stealthy_energy`, constant `TABLE_MIN_M = 75`, the midpoint of the measured interval 61 to 89): tables iff M >= 75, otherwise trig. No measured GPU relax case regresses under this rule (M < 75 uses the trig path, so it is identical to baseline). Consequences and limits: the CPU gains at small M (2.3x at M = 13) are given up so the rule stays backend independent; the threshold was measured only at d=3, N=100 and only on the A100, so other (N, d) are extrapolated.

Factory path used by the C++ reference trajectories (compared during development): d=2 N=64 (M = 34) and d=3 N=100 (M = 13) both use trig; forcing tables gives the same result (accepts equal, max abs ds 4.4e-16 both ways).

## Fix round T13: end-to-end timing through the CLI path (R32)

**Final rule: `make_stealthy_energy` always selects trig (`n_max=None`); `TABLE_MIN_M` is removed.** The table kernel stays reachable by constructing `StealthyEnergy(..., n_max=max|n|)` directly.

The R26 grid above timed `relax` with 200 evaluations per pass, so it had no compaction tail (all lanes run to the budget). Ensemble tasks run to convergence at tol 9.99999968e-21 with the batch compacting to small active sets. T13 re-measured on that path.

Job 16992894 (A100 80GB PCIe, JAX 0.12.0.1): `xla_cco.cli.relax` functions (`build_physics`, `make_settings`, `relax_batches`, batch size 1024, L-BFGS, tol 9.99999968e-21, `--stop-tol 0`), d=3, N=100, phi=0.05, 1200 unit-cell configurations from `cco_runs/p3d-N100-phi0.05-chi<chi>-val0.0/ic/chunk_000{0,1,2}`; path forced with `n_max=None` (trig) vs `n_max=max|n|` (tables). Each variant ran 3 times in one process; both orders (trig first, tables first, separate processes) agree to 1%. Cold = first call (includes compile of all compaction shapes); warm = mean of calls 2 and 3.

Tables are 1.03x faster at chi = 0.35 and 1.08x slower at chi = 0.45 (warm wall; per lane-eval 0.98x and 1.11x). The total eval counts differ by 1% to 3% (roundoff changes line-search paths) and every configuration succeeds on both paths. The result is ambiguous (mixed sign, within 8%), so ruling R32 applies: default to trig, which also removes a backend-dependent heuristic.

Caveats: one GPU model, d=3, N=100, two chi; the R26 numbers at M <= 61 (tables 0.44x) were not repeated.
